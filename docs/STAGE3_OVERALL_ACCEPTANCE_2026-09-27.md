## 原 P1：删除权限缺口（本批已修复）

位置：`qa_core/api/route_admin.py::admin_delete_document` → `scripts/rebuild_kb.py::delete_file_chunks`。

当前前者仅 require_roles(admin)，未要求 default 全局管理员、未按认证租户校验资产；后者按 filename/kb_version 找账本，再按 asset/version 删除向量，没有 tenant 条件。因此非 default 租户管理员也能进入全局候选资料删除流程。STAGED 写入锁只能保护版本状态和互斥，不能替代权限。


推荐首版最小修法：鉴于当前知识版本及发布指针是全局模型，先将全局删除操作收紧为 default 租户全局 admin，与 activate/rollback 的权限口径一致；如果需要租户管理员自助删除，再实现明确租户资产过滤及账本作用域，不只加向量 tenant filter 而留下跨租户账本删除。核查其他全局管理写入口是否同样漏边界，但不要直接重做多租户发布系统。

## 原 P2：联合回归中的撤回连接故障（本批已修复）

真实联合运行中，`test_publication_sandbox.py` 的 A→B 发布后撤回步骤返回 503。捕获日志明确为 route_kb.withdraw_source 调用缓存客户端 describe_collection 时抛 ConnectionNotExistException。此前其他集成/快照关闭了 URI 对应的共享连接别名；get_milvus_client 的进程级缓存仍返回旧对象，撤回入口没有像已有 query_with_retry 那样重建重试。这不是质量门禁拒绝、租户权限拒绝或数据库事务失败。

该错误失败关闭，未写共享撤回记录，也没有越权输出；但正常管理调用链可能因旧连接中断，属于可用性阻塞。单独沙箱及上一批 492 项均通过，不代表联合顺序也通过。本次不重跑单独沙箱来覆盖联合失败。

修复应集中管理断连客户端：只在明确连接不存在时重建并有界重试，覆盖撤回所用 describe/query，不将存储异常当作空账本继续操作；避免再次关闭共用连接而破坏其他请求。补“先建立缓存→关闭连接→撤回”的真实隔离用例及联合套件，保持真实门禁、锁和事务，不放宽错误处理或改执行顺序掩盖问题。
