# 第 7 步 D 阶段诊断报告：现有评测集为什么不能当"效果证据"

日期：2026-09-20
对象：`eval_sets/v4-r3.json`（89 条，SHA256 前缀 `2591a94216fe270b`，kb_version `v4-foundation-r3`）
方法：只读分析，未修改任何数据
结论：**该评测集只能作为开发诊断集使用，不能作为效果证据。** 已定位 5 项缺陷，其中 1 项（真值自相矛盾）直接污染了 7C 基线。

---

## 一、为什么先做诊断而不是直接重建

方案第 5 节要求"先造尺子，再改数据，最后调参"。重建评测集是 7D 的主体，
但"重建"必须先知道**要修掉什么**，否则只是换一批同样有问题的数据。

本报告给出量化依据，并据此确定 7D 的设计要求。

## 三、五项缺陷（量化）

### 3.1 缺陷一：没有 dev / regression / frozen 划分

用例字段全集里**不存在任何划分字段**：

```text
['category', 'difficulty', 'expect_hit', 'expect_reject', 'expect_route',
 'hard_negatives', 'id', 'note', 'query']
```

后果：这 89 条**同时充当调参集和验收集**。任何阈值、TopK、融合权重的调整都会
在这 89 条上"看到效果"，也就无法排除过拟合。

> 需要澄清一处口径：旧基线与项目材料中提到的
> "固定 dev/test 划分、用冻结 test 集验证选型"，依据的是**更早那一轮检索消融**
> （`reports/retrieval_ablation_v4_v3.json`，数据集 `v4`，确实带 dev(25)/test(12) 划分）。
> 但**当前这份 `v4-r3.json` 没有任何划分**。两者不是同一份数据，不能互相引用。

### 3.2 缺陷二：82% 的用例来自 5 个生成模板

把查询里的告警码、FAQ 编号、设备名、数字抹掉后归类：

| 模板 | 条数 | category |
|---|---:|---|
| `<设备> 告警对应的标准处置流程包含哪些步骤？` | 16 | retrieval |
| `<设备>出现<ALM>时，案例<FAQ>的第<N>类上下文应先核对什么？` | 25 | faq_exact |
| `<设备> 设备上报 <ALM> 告警，应该怎么处理？` | 16 | alarm_lookup |
| `对象为<X>,注入条件为<Y>,观测告警<Z>……的技术要点和适用条件是什么？` | 7 | retrieval |
| `<文档片段截断> 的技术要点和适用条件是什么？` | 9 | retrieval |
| **小计（生成模板）** | **73** | |
| 手写（问候 6 / 越界 4 / 域外 6） | 16 | direct / guardrail / reject |
| **合计** | **89** | |

**73/89 = 82% 出自 5 个模板。** 这意味着：

- 任何**按用例随机切分**的方案都会造成严重模板泄漏——同一模板的样例同时出现在
  dev 和 test，test 就退化成"记住模板"；
- 模板内只换了实体（告警码、设备名），考察的是实体抽取，**不考察语义理解**；
- 这与第 7 步那次消融"7 个变体 `Recall@5` 全为 1.0、彼此毫无区分度"直接吻合：
  尺子太钝，不是因为方案等价，是因为题都一样。

### 3.3 缺陷三（最严重）：同一句问话对应多个不同真值

有 5 组 query 完全重复，共 11 条用例，**且每条的 `expect_hit` 不同**：

| query | 用例 → 期望命中的文档 |
|---|---|
| `ALM-DNS-LAT 告警对应的标准处置流程包含哪些步骤？` | R02→`sop_operation_200.md`<br>R07→`sop_operation_080.md`<br>R09→`sop_operation_020.md` |
| `ALM-PTP-LOCK 告警对应的标准处置流程包含哪些步骤？` | R05→`sop_operation_048.md`<br>R06→`sop_operation_128.md` |
| `ALM-MME-ATT 告警对应的标准处置流程包含哪些步骤？` | R10→`sop_operation_158.md`<br>R11→`sop_operation_078.md` |
| `对象为DNS,注入条件为缓存命中率下降,观测告警ALM-DNS-LAT。……` | M02→`guide_experiment_040.md`<br>M03→`guide_experiment_020.md` |
| `对象为UDM,注入条件为订阅数据不一致,观测告警ALM-UDM-AUTH。……` | M13→`guide_experiment_034.md`<br>M15→`guide_experiment_014.md` |

**同一句问话不可能同时命中三个互相独立的文档。** 判定方式是
`expect_hit in got_sources`（子串匹配），这意味着：

- 对同一问话，"正确答案"取决于用的是哪一条用例，而三条的期望互斥；
- 这些用例的通过与否**取决于 top-5 里恰好落进哪一份同质文档**，属于抽奖；
- 它同时污染了分母（同一问话被计数 2~3 次）。

**与 7C 基线的直接关联**：7C 的 retrieval 未命中清单是
`R01 R03 R04 R06 R07 R10 R12 R14 M04 M10 M12`（11 条），其中
**R06、R07、R10 三条属于真值矛盾组**——即 `hit@5 = 0.767` 里至少有
**3/89 ≈ 3.4 个百分点是测量误差**，不是检索质量问题。

这说明 `hit@5` 目前**不是一个可信的数字**，无论向上还是向下解读。

### 3.4 缺陷四：hard negative 标注了但没有任何脚本消费

- 62/89 条带 `hard_negatives`，共 124 个；
- 分布：`faq_exact` 25/25、`retrieval` 32/32、`alarm_lookup` 5/16；
- `direct` / `guardrail` / `reject` 为 0（合理，它们不走检索）；
- **`scripts/run_eval.py` 中不存在对 `hard_negatives` 的任何引用**（grep 零命中）。

后果：无法计算 hard negative 违例率，也就无法回答"检索出来的东西是不是看似相关
但结论不同"。第 8 步的消融实验最需要这个指标。

### 3.5 缺陷五：部分 query 是文档片段拼接，不是真实问法

9 条 `retrieval` 用例的 query 是**文档正文被截断后直接接了问句后缀**，例如：

```text
警直接下结论。本卡关注"NR上行干扰升高"的定位阶段;证据应记录来源、时间、对象 的技术要点和适用条件是什么？
免只看进程存活。本卡关注"用户面时延升高"的发现阶段;证据应记录来源、时间、对象 的技术要点和适用条件是什么？
章节<N>-检查<N>:采集控制面成功率、用户面时延、丢包、CPU、内存和接口队列指标 的技术要点和适用条件是什么？
-检查<N>,如果关键上下文缺失,应停止自动处置并追问设备、版本、区域或变更编号。 的技术要点和适用条件是什么？
```

这些不是用户会问的话，真实用户不会把文档正文抄一半来提问。它们无法代表线上分布，
却占 `retrieval` 类的 28%。

## 四、语料结构：为什么"300~500 条"在当前语料上做不出来

这一节是采样 r3 原始文档后发现的，比评测集本身的缺陷更根本。

### 4.1 SOP：200 份文件，只有 20 个不同告警码

```text
SOP 文件数 200，有告警码 200，不同告警码 20
→ 每个告警码对应 10 份 SOP
   例：ALM-DNS-LAT → sop_operation_020/040/060/080/100/120/140/160/180/200.md
       ALM-PTP-LOCK → sop_operation_008/028/048/068/088/108/128/148/168/188.md
```

**这直接解释了缺陷三的成因**：旧生成器用
`"%s 告警对应的标准处置流程包含哪些步骤？" % code` 出题，而 10 份 SOP 共享同一个告警码，
于是**同一句问话被生成了 10 次，每次指向不同的文件**。

SOP 文本本身也是模板：

```text
<设备><主题>处置 SOP <NNN> 步骤 <M>:执行<动作>。针对<条件>记录对象、版本、时间和前后值;证据不足时停止并转人工复核。
```

200 份文件 = 20 个主题 × 10 次重复，差异只在 `SOP 编号`、`步骤号`、`动作词`。

### 4.2 doc_type 分布与命名不一致

| doc_type | 块数 | 文件数 | 说明 |
|---|---:|---:|---|
| `fault_case` | 750 | 750 | 每票一份，`SIM-TT-xxxxx`，各自独立告警码 |
| `sop` | 2200 | 200 | 20 主题 × 10 重复 |
| `manual` | 1350 | 60 | **混合了两种家族**：`manual_reference_*`（REF 知识卡 20 个）+ `guide_experiment_*`（EXP 实验指南 40 个） |
| `guide` | **0** | 0 | **不存在该类型**——旧生成器的 `--manual` 实际覆盖了两种家族 |

FAQ：1000 条，问题形如
`<设备>出现<ALM>时，案例SIM-FAQ-<NNNN>的第<N>类上下文应先核对什么？`
——**问句自带案例编号**，所以 `faq_exact` 类 `hit@5 = 1.0` 属于"编号精确匹配"而非检索能力。

### 4.3 结论：当前语料的有效主题数约为 20

把上面合起来看：整个 r3 语料围绕 **约 20 个（设备 × 故障主题）组合** 展开，
其余都是同一主题的重复采样。因此：

- **不能用"加题量"来提升评测集规模**。在 20 个主题上做 500 条，
  等于每个主题 25 条高度相似的题，评测集只会变得更"虚胖"，
  与第 3.2 节的模板集中问题同源；
- 评分上限被语料锁死：无论检索方案怎么改，都只能在同样 20 个主题上比较；
- 第 8 步"把评测集扩到 300~500 条"这条要求，**在当前语料上不具备成立条件**，
  必须以 8B（r4 数据改造，提高主题多样性）为前提。

**这是一条对第 8 步的重要修正**：不是"先建评测集、再改数据"，
而是 **"先诊断语料 → 改 r4 数据 → 评测集规模才能真实扩上去"**。
第 8 步 8A/8B 与 7D 之间存在双向依赖，8A 的产出（主题多样性诊断）应提前到 7D 阶段完成。

## 五、汇总判定

| # | 缺陷 | 影响 | 严重度 |
|---|---|---|---|
| 1 | 无 dev/regression/frozen 划分 | 调参与验证共用同一批数据，无法排除过拟合 | 高 |
| 2 | 82% 用例出自 5 个模板 | 随机切分必然模板泄漏；测不出方案差异 | 高 |
| 3 | **同一 query 多个互斥真值（5 组 11 条）** | **真值不可信，`hit@5` 至少 3.4 个百分点是测量误差** | **最高** |
| 4 | hard negative 无人消费 | 无法度量"看似相关但结论不同" | 中 |
| 5 | 9 条 query 是文档片段拼接 | 不代表真实分布 | 中 |

**结论**：`eval_sets/v4-r3.json` 的定位应改为

> r3 自动生成的开发诊断集，用于发现链路级缺陷（拼写/路由/装配错误），
> **不作为最终效果证明**。

## 六、7D 的设计要求

据此，重建评测集必须满足以下硬性条件，缺一不可：

1. **查重**：`query` 全局唯一，杜绝同一问话多个真值；
2. **真值唯一**：一条 query 只有一个 `expect_hit`；
3. **按模板分组切分**：模板是切分单位，不是用例。同一模板（含实体替换生成的变体）
   整体进同一边，避免泄漏；
4. **三层集合**：
   - `dev`：可反复调参；
   - `regression`：冒烟，用于每次改动的快速回归；
   - `frozen`：**调优期间禁止使用**，只在最终验收时跑一次；
5. **规模**：**不再以 300~500 条为目标**（见第四节：语料只有约 20 个有效主题，
   加题量只会造出高度相似的题）。改为"**在语料允许的范围内，给出互不重复的最大集**"，
   预期 150~250 条，并把"主题数不足"作为 8B 的输入，而不是用重复题把规模撑起来；
6. **难度分布**：hard 占比不低于 20%（当前 6.7%），hard 应来自
   - 相似告警码辨析、跨文档冲突、版本/时效差异、口语与错别字、多轮指代、
   - 无答案与证据不足；
7. **hard negative 可消费**：`run_eval.py` 必须计算 hard negative 违例率；
8. **真实问法**：query 必须像用户会说的话，禁止把文档正文截断后直接拼问句；
9. **元数据自述**：每条记录保留 `template_id`、`split`、`source_dataset`、
   `generator_version`、`seed`，且数据集顶部记录 SHA256 与生成参数。
